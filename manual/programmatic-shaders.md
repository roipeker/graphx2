# Programmable shaders

Most GraphX visuals should stay boring—in the best way.

Shapes, images, gradients, filters, and text cover a huge amount of 2D work with predictable rendering.

Sometimes you want pixels generated by a tiny GPU program instead: animated plasma, procedural noise, a water distortion, a custom signed-distance-field effect.

That is where fragment shaders enter.

## Flutter still owns shader compilation

GraphX does not invent another shader language.

The current Canvas shader path uses Flutter's build-time fragment-program assets.

Declare a shader in the Flutter project:

```yaml
flutter:
  shaders:
    - shaders/waves.frag
```

Then load the compiled program through the GraphX asset store:

```dart
final shader = await stage.assets.shader(
  'shaders/waves.frag',
);
```

GraphX caches the compiled `GShader` by default just like its other runtime assets.

Runtime source compilation is intentionally not emulated here; this API follows what Flutter's current Canvas backend actually supports.

## A program is reusable; an instance holds mutable uniforms

```dart
final program = await stage.assets.shader('shaders/waves.frag');
final shader = program.instance();
```

`GShader` is the reusable compiled program.

`GShaderInstance` owns one mutable native fragment-shader instance and its uniform/sampler bindings.

Set values by name:

```dart
shader.setFloat('u_time', 0);
shader.setColor('u_color', Colors.cyan);
```

or keep a stable hot-loop binding:

```dart
final time = shader.float('u_time');
```

then update it without looking the uniform up again:

```dart
time.value = stage.elapsed;
```

## `GShaderNode` gives the shader a rectangle in the scene

```dart
final visual = root.addChild(
  GShaderNode(
    shader,
    width: 320,
    height: 180,
  ),
);

visual.setPosition(60, 80);
```

The shader does not infer its geometry from its pixels or samplers. The node has an explicit GraphX width/height and therefore predictable bounds.

If the shader declares a `vec2 graphx_size` uniform, `GShaderNode` keeps it synchronized automatically when the node is created/resized.

That gives shader code an easy way to normalize fragment coordinates against the visual size.

## A tiny animated fragment shader

A Flutter fragment shader can look roughly like this:

```glsl
#version 460 core
#include <flutter/runtime_effect.glsl>

uniform vec2 graphx_size;
uniform float u_time;

out vec4 fragColor;

void main() {
  vec2 uv = FlutterFragCoord().xy / graphx_size;
  float wave = 0.5 + 0.5 * sin(u_time + uv.x * 12.0);
  fragColor = vec4(uv.x, wave, 1.0 - uv.x, 1.0);
}
```

Then a GraphX updater only changes the time uniform:

```dart
final time = shader.float('u_time');

root.onUpdate.add((delta) {
  time.value = root.stage.elapsed;
});
```

The `GShaderNode` listens to uniform changes and requests repaint automatically.

## Samplers can use GraphX textures

A shader can also read an image:

```dart
shader.setTexture('u_image', texture);
```

For portable sampler binding on backends where Flutter cannot resolve sampler names reliably, `GShader.instance()` accepts a name-to-declaration-index map:

```dart
final shader = program.instance(
  samplers: {
    'u_image': 0,
  },
);
```

That keeps the named GraphX-side API while using Flutter's numeric sampler path underneath.

## The instance has an explicit lifetime

A `GShaderNode` can share a `GShaderInstance` with another renderable when shared uniform state is intentional.

Because of that, disposing the node does **not** dispose the shader instance automatically.

The code that owns the instance should eventually call:

```dart
shader.dispose();
```

Do that only after all nodes/renderables using that instance are finished with it.

## Shaders are not the answer to every visual effect

Before writing a shader, ask whether the existing retained path already expresses the idea:

```text
solid/vector geometry      → GGraphics
linear/radial/sweep color  → GGradient
post-process subtree       → GFilter
simple color treatment     → GColorTransform
programmable rectangle     → GShaderNode
```

A shader earns its complexity when the visual is genuinely procedural or needs pixel math the higher-level primitives cannot express cleanly.

That keeps the fun part of shaders fun instead of making every button a graphics-programming project.
